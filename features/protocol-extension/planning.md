## Open questions — drafted 2026-09-05, RESOLVED 2026-09-06 (Q1–Q9 accepted with the user)

All nine questions below were signed off with the user across the 2026-09-05/2026-09-06 design
sessions; the "Recommended answer" column now records the accepted resolution (folded in place,
matching the pattern `features/analyze-mode/planning.md` used). The formal backlog entry is
`docs/todo/PROTO-03-open-protocol-extension.md`.

| # | Question | Recommended answer | Why this one |
|---|---|---|---|
| Q1 | TOML schema for `[[command]]` / `[[command.on_reply]]` — field names, arg/field types, array args? | **Revised 2026-09-06 to add block-send support** (see rationale). Top level: `ptc_version = 1`, `extends = "gomocup"`. Per command: `name`, `args = ["name:type", ...]`, and **either** `send = "<template>"` (single line — the v1-original design, still the default for simple commands) **or** a block form `send.open = "<line>"`, `send.repeat = "<template>"`, `send.close = "<line>"` (for a `YXBOARD`/`BOARD`-style multi-line command). `args` gains one new type: `repeat(coord, T...)` — a variadic, `done`-terminated group at the console (mirrors `!pos <moveText...>` / `PosSession`'s existing `done` terminator), which `send.repeat` iterates to emit one wire line per item. Per `on_reply`: `pattern = "<template with {name:type} captures>"`, `action = "<DSL string>"` — **unchanged, still strictly single-line** (see Q8). Scalar type set for non-repeated fields stays closed: `int`, `float`, `string`, `coord`. | Discussion 2026-09-06 found the real wire protocol already uses exactly this open/repeat/close shape — `GomocupProtocol::generateAnalyzeRequest()`/`generateMoveRequest()` (`src/engine/gomocup_protocol.cpp`) both emit `YXBOARD`/`BOARD`, one line per path coordinate, then `DONE`, returning `std::vector<std::string>` (every `IEngineProtocol::generate*` already returns a line vector, not a single string). The console side has the same "open, accumulate, `done`-terminate" convention in `CommandDispatcher`'s `PosSession` (`beginPosSession`/`handlePosSessionLine`/`finalizePosSession`). A `.ptc` command that needs to send a board-sync-style block (the user's `yxboard x,y,c x,y,c done` example) genuinely cannot be expressed by a single-line `send` template — this is a real completeness gap in the original design, not scope creep, since it mirrors a mechanism the app already ships. The earlier "no array types" call (2026-09-05) was about *rendering* primitives (VCF path / heatmap collection sinks, correctly deferred) — a different question from whether `send` can emit a multi-line wire block, which this revision answers narrowly without reopening that deferral. `on_reply` stays single-line only (Q8, reaffirmed 2026-09-06: the user confirmed block support is send-side only for v1). |
| Q9 | **New 2026-09-06**: does a `.ptc` command declare a *kind* — instant query vs. real search integrated with `EngineState`/Stop — and can `send` reference live `GameState` data (e.g. the current move path), not just user-typed console args? | Add `group = "<name>"` to each `[[command]]`, using the **same 6 non-`analysis` groups already shown in `!help`**: `board`, `config`, `database`, `debug`, `engine`, `info`. **`group = "analysis"` is out of scope for v1** — a `.ptc` command cannot declare itself as a real search integrated with `EngineState`/`SearchIntent`/Stop in this iteration. `yxAnalyzeOne` itself must be declared under a non-`analysis` group (e.g. `info`) for v1, meaning it does **not** transition `EngineState` and is not cancellable via Stop — an accepted trade-off, not silently swept under the rug. **Resolved 2026-09-06**: `send` gains `send.repeat_source = "$currentPath"` (an alternative/companion to iterating a `repeat(...)`-typed arg) — the loader precomputes, per path item, `i.x`, `i.y`, and `i.color` (alternating Black/White by index, same formula as `generateAnalyzeRequest`'s `(i % 2 == 0) ? 1 : 2`). All three fields are always available on `i`; **`{i.color}` is simply omittable from the `send.repeat` template string** when a command's wire format doesn't need it (e.g. `send.repeat = "{i.y},{i.x}"` for a coordinate-only query) — no separate "optional" flag needed, it's just string interpolation. | The user proposed reusing the console's own existing category taxonomy (`[analysis]`, `[board]`, `[config]`, `[database]`, `[debug]`, `[engine]`, `[info]` from `!help`) instead of inventing a new flag — each group already implies known behavior from its existing built-ins, so `group` classification is self-documenting. Tracing `EngineController::analyze()` showed *why* `analysis` is the hard one: its search-completion signal is a bare coordinate line via `protocol_->signal_move`, which `yxAnalyzeOne`'s `MOVEEVAL` reply shape never triggers — supporting it for real would need a new `SearchIntent` value, a `.ptc`-declared "this pattern completes the search" marker, and changes to `pendingStopFlush_`/Stop handling, i.e. real surgery on `PROTO-04`/`ANLZ-06`'s state machine. The user explicitly chose to defer that (2026-09-06) rather than risk it in v1 — matching this codebase's "three failed fixes → stop and question the architecture" caution around this exact state machine. `$currentPath` is host-trusted data read straight from `GameState::currentPath()` — no engine/`.ptc` influence beyond normal gameplay — so it needs no trust-boundary validation the way `on_reply` capture fields do, and its item count (≤ board size, ~400) doesn't interact with Q5's file-level limits (those bound the `.ptc` file, not runtime-generated line count). |
| Q2 | Grammar for the `action` mini-DSL. Operator set, block delimiters. | Explicit keywords, no significant whitespace: `if <expr> then <stmt>* (elif <expr> then <stmt>*)* (else <stmt>*)? end`. Expressions: comparisons (`== != < > <= >=`) combined with `and`/`or`/`not` only — **no arithmetic operators, no variables beyond the typed `on_reply` captures**. | Explicit `end` avoids a hand-rolled indentation-sensitive parser (fragile inside a TOML string, easy to mis-indent by hand). Dropping arithmetic keeps the interpreter a pure decision table — every expression is a boolean-provable comparison over already-typed, already-bounded fields, which is the simplest possible thing to unit-test exhaustively and the smallest possible surface at the trust boundary. |
| Q3 | Name-collision with an existing command name. | **Fail closed at load time**, checked against **two separate namespaces**: (a) the full `CommandDispatcher` internal-command registry (`analyze`, `play`, `stop`, `getpos`, `loadpos`, `new`, `pos`, `redo`, `rule`, `start`, `undo`, `info`, `db`, `clear`, `engine`, `send`, `about`, `help` — everything `registerBuiltins()` already registers, since Q7 puts extension commands in this same `!`-prefixed console namespace) and (b) any two commands within the same `.ptc` sharing a name. Loader rejects the whole file with a clear error naming the colliding command. No separate prefix requirement — see Q7. | Since Q7 places extension commands in the *same* `!`-namespace as built-ins rather than a separate `!ext` sub-namespace (per the console's own existing "Internal commands must start with `!`" rule, which the user pointed out `.ptc` should also follow), the real collision risk is a `.ptc` command shadowing e.g. `!play` or `!db` in `CommandDispatcher` itself — not the Gomocup wire-protocol keyword set, which is a different, unrelated namespace (console command name vs. raw engine-line text) and was the wrong list to check against. Fail-closed keeps the same "reject rather than silently misbehave" precedent as PROTO-01. |
| Q4 | Where the `.ptc` path lives in `EngineConfig` / how it's selected / restart requirement. | Add `std::string protocolExtensionPath` to `EngineConfig` (empty = no extension). `SettingsDialog` gets a file-chooser row filtered to `*.ptc`, next to the existing engine-path row. Takes effect only on `startEngine()`/`reloadEngine()` — **no live reload**; editing the field while the engine is running requires clicking the existing Reload button. | Matches the project's existing three-part config pattern (`model/config.h` + `SettingsStorage` + `SettingsDialog`) exactly, and reuses the reload semantics every other `EngineConfig` field already has — zero new lifecycle concept introduced. |
| Q5 | Load-time limits: max `if`-nesting, max sink calls/action, max commands/file, max file size. | `if`-nesting depth ≤ 4; sink calls per action ≤ 16; commands per `.ptc` ≤ 32; args per command ≤ 8; file size ≤ 64 KB. Loader rejects the whole file (fail closed, same as Q3) if any cap is exceeded. | Generous enough for every case discussed (including the deferred VCF/heatmap ones, which would need array types before hitting these caps anyway) while still being small enough that a pathological or corrupted `.ptc` can't produce a deeply nested interpreter call or a multi-MB parse. Picked as round, defensible numbers rather than derived from a real constraint — the plan already says to revisit only if a legitimate `.ptc` hits the ceiling. |
| Q6 | Hot-reload vs load-once. | **Load-once**, at `startEngine()`/`reloadEngine()` only. No file-watching. | Matches `reloadEngine()`'s existing role as "pick up new config" and avoids a whole class of correctness questions (command mid-flight when the table swaps underneath it) that live-reload would open — consistent with the "explicitly defer, don't design for it speculatively" call already made for Q8. |
| Q7 | How extension command names are surfaced/typed in the console. | **Same `!`-prefixed internal-command namespace as built-ins**, e.g. `!yxAnalyzeOne 7,7` — no separate sub-prefix. Registered into `CommandDispatcher` exactly like a built-in; `!help` lists them under a new group, e.g. `[extension]`. | Revised 2026-09-05: the console's own existing rule (shown in `!help`'s own banner — "Internal commands must start with `!`: they keep UI + engine in sync") already unifies every user-facing command under one prefix convention, and the user explicitly asked for `.ptc` commands to follow that same rule rather than inventing a second one. A distinct `!ext` sub-namespace (the original recommendation) would have been redundant given that rule already exists, and inconsistent with how every other command group (`[analysis]`, `[board]`, `[engine]`...) already shares the single `!` convention. |
| Q8 | Multi-line/streaming replies — accumulate before firing `action`, or strictly one-line-in/one-action-out? | **v1 is strictly one-line-in/one-action-out.** No accumulation state machine. **Reaffirmed 2026-09-06**: the send side gained block support (Q1 revision) but the user confirmed `on_reply` parsing does not need the same — reply lines in the real protocol are already one-shot (`MESSAGE`/`INFO`/coord), unlike the multi-line `BOARD`/`YXBOARD` send blocks. | No concrete use case named one yet (the `yxAnalyzeOne` example is single-line), and the existing `INFO`/PV accumulation machinery in `GomocupProtocol` (`currentPVIndex_`, `currentNumPV_`, ...) shows how much state-machine complexity that pattern actually costs once you build it — not worth paying before a real need shows up. |

## Implementation sequencing (Q1–Q9 resolved 2026-09-06 — sequencing ready; formalized as PROTO-03)

1. **Schema + loader** (`src/engine/protocol_extension.{h,cpp}`, new files): parse a `.ptc` file into
   an in-memory command table. Pure data structure — unit-testable with no GTK/subprocess
   dependency. Enforces the Q5 load-time limits; rejects on Q3 collisions.
2. **Mini-DSL interpreter**: statement/expression parser (`if/elif/else` per Q2) + a fixed sink
   dispatch table (the 5 whitelisted sinks). Unit-testable against a fake typed-field map, no
   engine/UI dependency — mirrors how `GomocupProtocol`'s own parsing is unit-tested today.
3. **`GomocupProtocol` integration**: optional extension table passed in at construction;
   `parseLine()` tries built-in parsing first, falls back to the loaded `on_reply` patterns only on
   no match.
4. **`ICustomCommandSource` interface** + `EngineController::sendCustomCommand()` reaching it via
   `dynamic_cast` (keeps `IEngineProtocol` itself untouched, per the hard constraint).
5. **`CommandDispatcher` wiring**: register each loaded extension command name (Q7 decides the
   surface) after engine start; handler forwards args to `sendCustomCommand()`.
6. **New signal + UI wiring**: `EngineController::signal_custom_action` (or similar) carrying a
   tagged sink-call struct; wired in `main_window.cpp` to (a) a new small dynamic row container
   inside `EngineStatusView` for `set_status_field(name, value)` — `.ptc` names are arbitrary, so
   this can't reuse the 6 fixed label-pair members (`labelDepth_`/`valueDepth_`, ...) as-is; it adds
   a label pair the first time a name is seen and updates it thereafter, (b) an inline banner
   (following the existing crash-banner pattern — no libadwaita `Adw::Toast`, per `EngineStatusView`'s
   own comment) for `toast()`, and (c) `EngineLogModel` passthrough for `log()`. No board-drawing
   code — `highlight_cell`/`clear_highlights` were dropped from the sink whitelist 2026-09-06 (see
   user_story.md), so this step touches zero `BoardRenderer`/`BoardViewModel` code.
7. **`EngineConfig` + `SettingsDialog`**: file picker for the `.ptc` path (Q4).
8. **Regression tests**: schema parsing (valid + malformed `.ptc`), DSL interpreter (bounds
   enforcement, type mismatches, sink whitelist), name-collision rejection, end-to-end
   fake-engine-line → sink-call assertions. Every fix/feature in this codebase ships with a
   regression test per `CLAUDE.md`'s bug-fix workflow section — same expectation applies here since
   this is new, testable logic in `engine/`.

## Follow-ups (explicitly deferred, not to be folded into this feature)

- Brand-new non-Gomocup protocol family via `.ptc` (see user_story.md "Out of scope").
- UI-triggered custom commands (context menu / generated button).
- Board-cell visualization sinks (`highlight_cell`/`clear_highlights`, winrate-gradient or
  otherwise) — dropped from v1 2026-09-06; would need a new `BoardViewModel` field + `BoardRenderer`
  layer, and no concrete use case has needed it over `set_status_field` yet. Revisit only if one does.
- **`group = "analysis"` custom commands** (Q9, 2026-09-06) — a `.ptc` command that behaves as a real
  search: transitions `EngineState`, is cancellable via Stop, participates in `pendingStopFlush_`.
  Needs a new `SearchIntent` value, a `.ptc`-declared "this `on_reply` pattern completes the search"
  marker, and care around `PROTO-04`/`ANLZ-06`'s existing state machine. Deferred whole — v1 ships
  only the 6 non-`analysis` groups (instant commands, no `EngineState` change).
- **Live-`GameState` context in `send` templates** (Q9) — **RESOLVED 2026-09-06 and IN v1**: `send`
  gains `send.repeat_source = "$currentPath"`, with the loader precomputing `i.x` / `i.y` /
  `i.color` per path item (Black/White by index, same formula as `generateAnalyzeRequest`). See the
  Q9 row above for the accepted shape. No longer an open follow-up.
- Sink types beyond the 3 whitelisted (freeform drawing/annotation layer).
- Hot-reload of `.ptc` mid-session (Q6, if the load-once answer turns out to be too restrictive in
  practice).
